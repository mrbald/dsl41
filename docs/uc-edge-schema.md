# UC workflow record schema — U3a doc-frozen base subset

Status: FROZEN (base subset) 2026-07-28 · DL-55. Verified against the current
docs.stonebranch.com site (product selector "8.0", footer build stamp
"v2026.07.5"), fetched raw and quoted from the saved bytes on 2026-07-28;
corroborated by two OSS clients (gomleksiz/uac-api, OptionMetrics/
terraform-provider-stonebranch). NOT validated against a live controller —
the write path (one live POST + GET readback) is the U3b residue
(`# PENDING: U3b` in backend_uc.py).

## Scope — the U3 split (DL-55, the U6/Q2 pattern)

- **U3a (this document):** the CREATE-ONLY whole-record JSON shape for a
  workflow task whose edges carry one of the three base condition tokens
  (`Success`, `Failure`, `Success/Failure`). `compile_to_uc` emits exactly
  this subset.
- **U3b (open):** rich condition forms (Exit Code / Step Condition /
  Variable + `variableCondition`, vertex-level `conditionExpression`), the
  live `/resources/openapi.json` pull, and write-path verification. DL-08
  still stands: the API *client* is generated from OpenAPI, never
  hand-written — this document freezes records, not calls.

## The record (create shape)

`POST http://<controller>/uc/resources/task`, one record per workflow
("Creates a new Workflow task." — Workflow Task Web Services). Minimal
create subset emitted by `dsl41 uc`:

```json
{
  "type": "taskWorkflow",
  "name": "nightly_batch",
  "retainSysIds": false,
  "workflowVertices": [
    {"task": {"value": "extract"}, "vertexId": "1", "vertexX": "90", "vertexY": "90"},
    {"task": {"value": "load"}, "vertexId": "2", "vertexX": "90", "vertexY": "270"}
  ],
  "workflowEdges": [
    {
      "condition": {"value": "Success"},
      "sourceId": {"value": "1"},
      "targetId": {"value": "2"},
      "straightEdge": true
    }
  ]
}
```

## Field freeze (verbatim provenance)

- **`type`**: literal `"taskWorkflow"` — the doc's own full JSON example
  (`"type": "taskWorkflow"`, Workflow Task Web Services); independently the
  terraform provider hard-codes `Type: "taskWorkflow"` (task_workflow.go).
- **`name`**: required ("Y" in the All Tasks Properties table). NO
  character-set/length constraint is documented for the task `name` field
  (searched the property tables; NOT FOUND — unlike e.g. calendar names,
  which carry "Maximum 100 alphanumeric"). Consequence: job/box names pass
  through verbatim; an invalid name fails loudly at create time on the
  controller, and every bundle records this as an assumption note.
- **`retainSysIds`**: a RECORD attribute (JSON top-level field; "In XML web
  services, retainSysIds is specified as an attribute in the `<task type>`
  element."), NOT a URI/query parameter. "If retainSysIds is false and
  sysId is included in the request/response, sysId will be ignored; it will
  be autogenerated by the Controller. … Valid values: true/false (default
  is true)." Emitted records pin `false` (belt and braces on top of
  omitting sysIds).
- **`sysId`** — "Persisted only if retainSysIds is set to true." Omitted.
- **`version`** — "For Read and List task web services". Omitted on create.
- **`exportReleaseLevel`**, **`exportTable`** — both "read only". Omitted.
- **`workflowVertices[]`** — per vertex: `task` is a value wrapper
  (`{"task": {"value": "Sleep 0"}}`); `vertexId` is an explicit STRING in
  the whole-record shape (doc example: `"vertexId": "2"`) and edges
  reference it; `vertexX`/`vertexY` are optional strings ("Default is 0.").
  `alias`/`conditionExpression` are nullable and omitted (aliases exist for
  duplicate tasks in one canvas — impossible v1: task names are
  catalog-unique and appear once per workflow).
  Note: the *incremental* endpoint (`POST /resources/workflow/vertices`)
  server-assigns vertexId; the whole-record create carries explicit ids —
  the base serializer uses the whole-record form only.
- **`workflowEdges[]`** — per edge: `condition` is a value wrapper
  (`{"value": "Success"}`); `sourceId`/`targetId` are value wrappers whose
  `value` is the vertexId string ("Vertex ID of the source task." /
  "Vertex ID of the target task."; the `taskName`/`taskAlias` attributes
  seen on read are decorative — only `value` is required on create);
  `straightEdge` boolean, "Default is true."; `points` exists only for
  bent edges (omitted — every emitted edge is straight).

## Base condition tokens (the frozen enum)

Dependency-services condition property (tokens verbatim; the table's
multi-line list reflowed here to one slash-separated line): "Valid values:"
Success / Failure / Success/Failure / Approved / Approval Required /
Exit Code … / Step Condition … / Variable; "Default is Success." The third
base token is spelled **`Success/Failure`** (forward slash), confirmed by
the doc's own worked examples (`<condition>Success/Failure</condition>`).

There is NO `Cancelled` edge condition: zero occurrences across the fetched
web-services/properties pages and both OSS client source trees. The twin's
`cancelled` edge condition (DL-16a, the M06 t() mapping) therefore has no
base wire encoding — such edges quarantine their workflow (below).

Caveat, verbatim: "Success/Failure and Failure are not valid for Workflow,
Timer, and Manual tasks." Our reading (inference, not quote): a
source-task-type constraint — consistent with resolved U2 (a workflow
instance is never Failed). Unreachable in v1 output, which emits only
flattened leaf-task vertices (DL-16 M18 v1); it becomes load-bearing when
sub-workflow nesting lands.

## Excluded rich forms (U3b residue)

- `condition type="Exit Code"` — "Format: Numeric. Use commas to list a
  series of exit codes; use hyphens to specify a range. Example: 1,5,
  22-30".
- `condition type="Step Condition"` — "Format:
  step:procedure:program:condition codes. Example: *:*:*:JCLERR" ("Step
  Condition is valid for z/OS tasks only.").
- `Variable` condition + the edge's `variableCondition` element
  (`firstValue` / `operator` / `secondValue`).
- Vertex-level `conditionExpression` (boolean AND/OR over upstream vertex
  conditions; `logicalOperator` + nested `conditions[]`).
- Schema-shape conflict flagged for live verification: the community
  openapi.yaml (7.9.1.0, reverse-engineered, PARTIAL confidence) declares
  `ConditionWsData` as `{vertexId, type}` with no `value` field, conflicting
  with the doc's verified `{"value": "Success"}` example — the doc wins
  here; re-check on the live OpenAPI pull.

**Serializer consequence (the codex safe-freeze rule, 2026-07-12 audit):**
any edge outside the three base tokens — including the twin's `cancelled`
and any `var_condition` — QUARANTINES its whole workflow: the record is not
emitted, every offending edge is listed in the bundle's quarantine ledger,
and no partial workflow ever ships. No silent edge drop (DL-04).

## Apply-time requirements

- Referenced tasks must already exist on the controller: vertices reference
  tasks by name, and task bodies (agents, credentials, commands) are
  estate-specific — NOT part of this freeze. A create against a missing
  task name fails loudly; the bundle's notes list every referenced name.
- One `POST /uc/resources/task` per record; the bundle file is dsl41's
  artifact, not a UC bulk-import file.
- `retainSysIds: false` + no sysIds anywhere → the controller autogenerates
  all ids; records are environment-portable.
